# Operator-held backup and disposable account rehearsal — proposed, not authorisation

## Backup first
Free plan: hosted downloadable daily backups are unavailable. Use the current official Supabase CLI guide https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore and https://supabase.com/docs/guides/platform/backups. A workspace export is not a complete database backup.

Use an operator-controlled computer with encrypted storage, Docker and the current supported Supabase CLI; check version and db dump --help before use. Create a new local folder outside any sync or git directory. Obtain the session pooler connection details from the project's Connect dialog; do not send the URL or password in chat or place it in a command committed to a file. Use a locally protected environment variable or password prompt. Follow the official guide to produce roles, schema and data dumps. Do not reset the database password simply to perform a backup. Do not enable paid services. Treat all dumps as sensitive, including auth records, token material and password hashes. Encrypt before storage, keep access restricted, verify SHA-256 checksums and retain a separate encrypted copy. Record time, CLI version, database version and scope privately. Confirm coverage of auth, custom private schemas, storage objects, Edge Functions, secrets/settings and external providers separately; a logical database dump alone does not cover these. Keep secrets in an appropriate credential manager. Never upload the dump to the public repository or CI artifact.

Restore only into a separately approved isolated compatible environment. No hosted project creation, production restore, migrations or credential reset in this procedure. Compare table counts, constraints, RLS policies, fixture data, account ownership and login behavior; reconcile provider credentials separately. Synthetic CI rehearsal already passed; actual hosted backup and restore remain unverified.

## Disposable account rehearsal
Use an owner-controlled unused email identity, distinct from the two existing accounts. Explicitly approve creation first. Record the new account ID privately and validate exact ID against the dedicated test email. Do not grant access to paid AI, research, Stripe or marketplace features. Use a separate browser session and synthetic listing and research record. Verify the test account sees only its own records, and original accounts remain unchanged. Export the synthetic workspace. Record only counts and outcome, never identifiers or customer content in GitHub.

Before deletion, obtain explicit approval for that specific disposable account; ensure no real payment, marketplace connection, storage object or real support request is linked. Sign out all test sessions and revoke temporary Cloudflare access where applicable. Verify session expiry or server-side revocation; deleting an auth user is not itself immediate JWT invalidation. Use authorised Auth administration rather than manually deleting auth.users via SQL. Review account-specific AI usage separately since it has no cascading FK. Verify all six cascading relationships and the remaining usage table, compare aggregate counts and unrelated records, and review provider logs/backups and retention obligations. Do not delete either original account or run an unscoped DELETE. If any ambiguity, stop before deletion. This is an operator-led rehearsal; not automated production account deletion.
